# Strategy v2 Experiment Plan

## Цель

Этот документ описывает безопасный план тестирования `Strategy v2` без изменения:

- `DecisionEngine`
- `strategy_weights.json`
- `candidate_weights.json`
- боевой торговой логики

Цель плана: проверить, есть ли достаточно сильные основания для перехода с `Strategy v1.0` к `Strategy v2.0`, не затрагивая live-ядро до подтверждения данными.

## 1. Главная гипотеза v2

Основная рабочая гипотеза:

- `Structure: 0.25 -> 0.20`

Это главный кандидат на v2, потому что по `strategy_experiments_report.json` именно сценарий `structure_weight_0.20` показал лучший профиль против baseline:

- winrate: `20.0%` vs baseline `18.75%`
- profit factor: `0.46` vs `0.37`
- average PnL: `-115.19` vs `-153.62`
- max drawdown: `-1727.85` vs `-2457.85`

Это ещё не основание для внедрения, но это лучший подтверждённый кандидат на следующий цикл тестов.

## 2. Почему Momentum пока НЕ ослаблять

По `blocked_trade_simulation_Momentum_report.json`:

- найдено `53` Momentum-blocked кандидата
- `WIN`: `0`
- `LOSS`: `16`
- `EXPIRED`: `37`
- winrate: `0.0%`
- profit factor: `0.0`
- average R: `-0.36`

Вывод:

- `Momentum` действительно часто блокирует сигналы;
- но blocked simulator не подтверждает, что эти заблокированные сделки стоило бы открывать;
- поэтому ослабление `Momentum` сейчас не имеет статистического обоснования.

Правило для v2:

- `Momentum` не ослабляется до тех пор, пока новые blocked-trade tests не покажут устойчивое улучшение по PnL и PF.

## 3. Почему Risk НЕ усиливать

По `strategy_experiments_report.json` сценарий `risk_weight_0.20` хуже baseline:

- winrate: `13.33%`
- profit factor: `0.16`
- average PnL: `-219.17`
- max drawdown хуже baseline

Вывод:

- усиление `Risk` не улучшает качество сигналов;
- наоборот, текущие данные показывают ухудшение торгового профиля.

Правило для v2:

- `Risk` не усиливается в следующем цикле тестов;
- любые идеи по `Risk` можно рассматривать только после того, как появится более широкая статистика по закрытым сделкам и blocker-specific simulation.

## 4. Какие тесты запускать

### Тест 1. Baseline

Цель:

- зафиксировать контрольную точку для всех сравнений.

Что сравниваем:

- текущие веса и текущую логику без изменений.

### Тест 2. Structure 0.20

Цель:

- проверить главный кандидат v2 в повторяемом offline-сценарии.

Что меняется в тесте:

- только `Structure: 0.25 -> 0.20`

Что не меняется:

- `Momentum`
- `Risk`
- decision rules

### Тест 3. Structure 0.20 + Momentum 0.25

Цель:

- проверить кандидатную схему перераспределения весов, не ослабляя сам `Momentum` filter/gate.

Тестовый набор:

- `Trend: 0.40`
- `Structure: 0.20`
- `Momentum: 0.25`
- `Risk: 0.15`

Важно:

- это не тест ослабления `Momentum` threshold;
- это только test of weight allocation.

### Тест 4. Symbol-specific Structure test

Цель:

- проверить, одинаково ли полезно снижение `Structure` для:
  - `BTC`
  - `ETH`
  - `SOL`

Зачем это нужно:

- research уже показывает различия по near-setup поведению и по слабым фильтрам;
- поэтому единое изменение может работать по-разному для разных символов.

### Тест 5. Regime-based Structure test

Цель:

- проверить, даёт ли `Structure 0.20` преимущество в зависимости от режима рынка:
  - `Trending Up`
  - `Trending Down`
  - `Range`
  - `High Volatility`
  - `Low Volatility`

Важно:

- regime-based analysis используется только как аналитический слой;
- до накопления достаточной historical regime history это не должно менять live-логику.

## 5. Какие метрики сравнивать

Для каждого теста должны сравниваться следующие метрики:

1. `Winrate`
2. `Profit Factor`
3. `Average PnL`
4. `Max Drawdown`
5. количество `SETUP`
6. количество `HIGH PRIORITY`
7. количество ложных сигналов
8. результат по `BTC / ETH / SOL`
9. результат по `LONG / SHORT`
10. результат по режимам рынка

Дополнительно полезно отслеживать:

1. общее количество сигналов
2. количество `NO TRADE`
3. долю blocked signals
4. стабильность результата на нескольких окнах, а не на одном запуске

## 6. Минимальные условия для внедрения

Любое изменение может рассматриваться как кандидат на переход в v2 только если одновременно выполнены все условия:

1. `30+` закрытых сделок
2. `Profit Factor` лучше baseline минимум на `0.10`
3. `Winrate` не хуже baseline
4. `Max Drawdown` меньше baseline
5. `Average PnL` лучше baseline
6. `data_quality = OK`
7. `auto_learning` не должен блокировать изменение

Если хотя бы одно условие не выполнено:

- изменение не переносится в боевую конфигурацию;
- оно остаётся на уровне research / candidate / experiment.

## 7. Порядок тестирования

### Этап 1. Offline experiments

Сначала запускаются только offline tests:

1. `baseline`
2. `Structure 0.20`
3. `Structure 0.20 + Momentum 0.25`
4. `symbol-specific Structure`
5. `regime-based Structure`

Цель:

- понять, есть ли устойчивое улучшение без вмешательства в live-систему.

### Этап 2. Candidate-level validation

Если offline tests выглядят лучше baseline:

- формируется или обновляется кандидатная конфигурация;
- но `strategy_weights.json` остаётся без изменений.

Цель:

- проверить, что improvement не является случайным эффектом одного отчёта или короткого периода.

### Этап 3. Paper / live observation

После offline-подтверждения:

- кандидат наблюдается в paper-style режиме или через аналитическое сравнение с live baseline;
- decision flow и фактические торговые результаты мониторятся отдельно.

Цель:

- убедиться, что улучшение не исчезает в более реалистичной среде.

### Этап 4. Только ручное approval

Только после выполнения всех минимальных условий:

- готовится отдельное подтверждение на изменение боевой конфигурации;
- решение принимается вручную.

Автоматическое применение запрещено.

## 8. Что можно менять только после подтверждения

Только после прохождения всех этапов и выполнения минимальных условий можно обсуждать:

1. перенос кандидата в боевые веса;
2. пересмотр `Structure` внутри основной стратегии;
3. symbol-specific adjustments;
4. regime-aware adaptations;
5. более глубокий пересмотр decision thresholds.

До этого момента все такие изменения остаются только исследовательскими.

## 9. Что запрещено

Запрещено:

1. сразу применять веса в `strategy_weights.json`;
2. ослаблять `Momentum` без новых доказательств;
3. усиливать `Risk`;
4. менять `DecisionEngine` без отдельного подтверждения;
5. переносить в live любые изменения только потому, что они увеличили число сигналов;
6. игнорировать `data_quality` и blocker-аналитику при принятии решения.

## 10. Итоговый безопасный маршрут v1.0 -> v2.0

Безопасный маршрут сейчас выглядит так:

1. оставить `v1.0` без изменений;
2. считать baseline контрольной точкой;
3. главным кандидатом тестировать `Structure 0.20`;
4. не ослаблять `Momentum`, пока blocked simulator показывает отрицательный результат;
5. не усиливать `Risk`, потому что experiments уже показали ухудшение;
6. подтверждать изменения только через offline -> candidate -> observation -> manual approval.

Финальный вывод:

на текущем этапе `Structure 0.20` — это основной и наиболее безопасный кандидат для `Strategy v2`, но переход к live-внедрению допустим только после строгого подтверждения метриками и качеством данных.
